# Design

## Context

See `proposal.md` — Why, and the `wasm-build-pipeline` / `interval-rounding` spec
deltas for the required behavior. Facts established while planning against the
current tree and the pinned dependencies:

- `vendor/libfive` is generated by `scripts/vendor-libfive.sh` from pin
  `918387a…` with patches `0001`–`0003` already applied (AD-016, AD-021).
  `build/deps/{eigen,boost}` are populated and verified by
  `scripts/fetch-deps.sh`. No compiler has ever run against either tree.
- Upstream's CMake declares `libfive` and `libfive-stdlib` as `SHARED`
  libraries. Emscripten has no general shared-library model without side
  modules, so a carried patch must select static archives.
- Upstream's mesher spawns work with `std::async(std::launch::async, …)` even
  when `settings.workers == 1`. Reachable call sites for the v1 (dual-contouring)
  path are `render/brep/worker_pool.inl`, `render/brep/dual.hpp`,
  `render/brep/object_pool.inl` and `render/brep/brep.hpp`; the progress thread
  in `progress.cpp` is only started when a progress handler is set, which the C
  API never does. Without pthreads, Emscripten's thread entry points are stubs
  that fail at runtime, so `std::async` must not be reached (AD-008, AD-014).
- Boost 1.92's `rounded_arith_exact` and `rounded_transc_exact` do **not**
  widen: both `*_down` and `*_up` return the plain result, and
  `rounded_*_std` depends on fenv rounding modes. There is therefore no stock
  Boost policy that satisfies AD-015; the policy must be ours.
- The C API returns `libfive_interval`/`libfive_vec3` by value and accepts
  `libfive_vec3`/`libfive_region3`/`libfive_vars` by value; most C stdlib
  functions accept `tvec2`/`tvec3` by value. JavaScript cannot pass or receive
  struct-by-value arguments, so the core surface needs shims. The stdlib
  pointer-shim surface belongs to `stdlib-bindings` (roadmap item 5).
- `libfive_tree_render_mesh_coords`, `render_slice*`, `render_pixels`, the
  save/load family and `libfive_tree_print`'s companions are compiled by the
  vendored CMake but are outside the v1 surface (AD-018; `architecture.md`
  "not in v1"). Only `libfive_tree_render_mesh_st` may be reachable.
- This container has no emsdk; Emscripten 3.1.64 and Node live on the SSH
  verification server, and CI uses `mymindstorm/setup-emsdk@v14`. The build
  script must therefore assert the toolchain rather than assume it.
- `build-wasm.yml` already calls `scripts/build-wasm.sh` when it exists, and
  `publish-npm.yml` calls it before `npm publish`. No JS package exists yet, so
  the build stops at `dist/libfive.{wasm,js}` this change.

## Goals / Non-Goals

**Goals:**

- One command compiles the pinned kernel and produces the shipped artifact,
  with the toolchain, flags, export list and ABI pinned in the repository.
- The interval policy is enforced by tests that fail on undersized bounds, so
  AD-015 is proven rather than asserted.
- The export surface and shim signatures are frozen and documented, giving
  `js-package-core` a stable target.
- CI exercises the real build on every push while keeping the workflows'
  existing contract.

**Non-Goals:**

- Any TypeScript/JavaScript package code, loader, `Shape`, `Mesh`, or stdlib
  wrapper (roadmap items 3–5).
- Threads, SIMD, slices/pixels/file APIs, `--host=native`, golden images, or
  publishing (items 5–8).
- Narrowing the Boost header tree; the build measures what compiles and that
  question is answered by the artifact, not by hand-pruning headers.

## Decisions

### D1. One shell entry point orchestrating CMake/Emcc, not a second build system (AD-019)

`scripts/build-wasm.sh` is a Bash script (`set -euo pipefail`, reusing
`scripts/lib/vendor-common.sh`) with this pipeline:

1. Load `LIBFIVE_EMSDK_ENV` if set and `emcc` is missing, then require
   `emcc`/`emcmake`; assert `emcc --version` names exactly `3.1.64` (AD-013).
2. Run `scripts/vendor-libfive.sh` and `scripts/fetch-deps.sh` (both idempotent;
   they verify pins/digests before compiling). `--check` is used when the trees
   already exist so a damaged tree fails before a long compile.
3. `emcmake cmake -S vendor/libfive -B build/wasm -G Ninja -C scripts/emcache.cmake`
   plus `-DEIGEN_INCLUDE_DIRS`, `-DBoost_INCLUDE_DIRS`,
   `-DLIBFIVE_WASM_INCLUDE_DIR` pointing at the absolute repo paths.
4. `cmake --build build/wasm --target libfive libfive-stdlib -j N`.
5. Link with `emcc`: `wasm/shim.c`, `libfive.a`, `libfive-stdlib.a`, the flag
   table from `build-system.md`, `wasm/exports.txt`, and a generated link
   response file; output `dist/libfive.js` + `dist/libfive.wasm`.
6. Run `node scripts/test-smoke.mjs` and `node scripts/test-interval.mjs`
   against the new artifact, print the wasm SHA-256 and size.

Flags documented as "evaluate in the build change" are resolved here:
`-flto` is adopted for release and omitted from the debug flavor. Measured at
apply time: the release wasm went from 1,070,253 to 1,046,998 bytes (~2.2%
smaller) with both suites green, while debug stays LTO-free for debuggability.
`--closure 1` is rejected for v1 because it adds a Java/Closure dependency and
obscures the ES6 glue that the loader work must debug — revisit in
`npm-packaging`.

Alternatives: an npm-scripts pipeline (no `package.json` yet and it would make
Node a build requirement), or committing generated Makefiles (loses the CMake
target graph upstream maintains). Shell + CMake matches the CI contract and the
existing scripts.

### D2. Static archives via a carried patch; link the artifact directly with emcc (AD-004, AD-008)

Patch `0004-static-library-targets.patch` makes the two `add_library(... SHARED)`
declarations honour a `LIBFIVE_LIBRARY_TYPE` cache variable (default `SHARED`
for native use). The overlay sets it to `STATIC`; the script links the archives
into one module with `emcc`. Build logic stays in upstream's CMake target graph,
and `--host=native` later reuses the same tree with the default.

Because an archive member is only pulled in when referenced, every exported
symbol is passed to the linker as `-Wl,--undefined=<symbol>` (in the generated
response file) alongside `-sEXPORTED_FUNCTIONS`. This avoids `--whole-archive`
(which would drag in filesystem/i18n objects irrelevant to v1) while
guaranteeing the exports exist; the smoke test verifies the runtime export
table. Alternatives: side modules/`SIDE_MODULE` (extra loader complexity, no
benefit for one artifact) and hand-maintained source lists (duplicates CMake
and drifts on pin bumps).

### D3. Initial-cache overlay for host guards and injected includes (AD-008, AD-014, AD-016)

`scripts/emcache.cmake` is the single place for build-shape knobs: build type,
`LIBFIVE_LIBRARY_TYPE=STATIC`, tests/GUI/Guile/Python off, `-fexceptions`,
release/debug optimisation flags, and include-root wiring for the wasm-only
interval header. CMake processes the initial cache **before** `-D` values, so
validation of the command-line include roots and the flavor-specific flags live
in a post-`project()` companion, `scripts/emvalidate.cmake`, included through
`CMAKE_PROJECT_INCLUDE`. Dependency paths are passed on the command line because
they are absolute and repo-relative; the companion validates that
`EIGEN_INCLUDE_DIRS`/`Boost_INCLUDE_DIRS`/`LIBFIVE_WASM_INCLUDE_DIR` are set and
exist (the existing patches also fail loudly). The link line uses the locked flag
table: `MODULARIZE=1`, `EXPORT_ES6=1`, `EXPORT_NAME=createLibfiveModule`,
`ENVIRONMENT=web,node,worker`, `ALLOW_MEMORY_GROWTH=1`, `INITIAL_MEMORY=64MB`,
`MAXIMUM_MEMORY=2GB`, `FILESYSTEM=0`, `USE_LIBPNG=1`, `--no-entry`,
`-fexceptions`, and the runtime methods the tests need
(`HEAPU8/HEAPF32/HEAPU32/HEAP32`, UTF-8 helpers, `getValue`/`setValue`). No
`-pthread`, no SIMD flags.

Debug flavor: `build/wasm-debug` with `-O0 -g4 -sASSERTIONS=2` and output under
`dist/debug/`, so invoking the debug flag never replaces the release artifact.

### D4. Single-worker mesher call sites run inline under Emscripten (AD-008, AD-014)

Patch `0005-single-threaded-mesher.patch` guards the four reachable async sites
with `#if defined(__EMSCRIPTEN__)`: the loop body runs synchronously on the
caller's thread instead of creating futures. Native builds keep upstream's
`std::async` paths untouched (needed by the future `--host=native` cross-check).
No pthread APIs are compiled into the wasm artifact, which is stronger than
relying on Emscripten's pthread stubs, and it matches AD-014's "worker-pool
sources compile but never execute" with an explicit proof: the interval and
smoke tests mesh successfully, and a symbol scan of the artifact shows no
pthread imports.

Alternatives: building with `-pthread` (forbidden by AD-008 and unnecessary for
one thread), patching only `settings.workers` (does not remove `std::async`), or
patching at one site (the others remain reachable).

### D5. A repo-owned software rounding policy, selected by a carried patch (AD-015, AD-023)

`wasm/include/libfive_wasm/interval_rounding.hpp` defines
`rounded_arith_soft<T>` and `rounded_transc_soft<T>`:

- arithmetic operators and conversions evaluate in `double` and widen the
  float result outward with `std::nextafterf` (down for lower bounds, up for
  upper bounds);
- transcendental functions evaluate the `double` libm result and widen the
  float cast outward the same way; `sqrt`/floor/ceil follow the same pattern;
- `init`/`downward`/`upward`/`to_nearest` are no-ops and `force_rounding`
  returns its argument, so no fenv routines are referenced;
- the policy is wrapped in `save_state_nothing` and paired with
  `checking_base<float>`, mirroring the shape of upstream's alias in
  `eval/interval.hpp`.

Patch `0006-software-interval-rounding.patch` includes the header (through the
overlay-provided include directory), replaces the alias's
`save_state<rounded_transc_std<float>>` with the software policy, and leaves the
rest of `Interval` untouched. The `__USE_ISOC99` workaround is neither defined
nor needed. Rationale for one-ulp outward widening: float inputs are represented
exactly, the double evaluation has far more precision than one float ulp, so the
outward step covers representation error for arithmetic and for correctly
rounded-enough libm results; the interval suite's tightness caps keep the
widening from degrading meshing. If the custom policy turns out to be
intractable at the pin (roadmap's stated fallback), the fallback is vendoring a
patched interval header — never accepting `fesetround` behavior.

Alternatives: Boost `rounded_*_exact` (verified not to widen in 1.92),
`rounded_*_std` (fenv-based, stubbed under wasm), and the PoC's
`__USE_ISOC99` shortcut (explicitly rejected by AD-015).

### D6. Shim only the core C ABI; freeze the surface through a manifest + README (AD-004, AD-011)

`wasm/shim.c` wraps exactly the pain points JavaScript cannot express:

| Shim | Why |
|---|---|
| `shim_region3_set`, `shim_vec3_set` | build `libfive_region3`/`libfive_vec3` in wasm memory |
| `shim_tree_eval_f` | original takes `libfive_vec3` by value |
| `shim_tree_eval_r` | original returns `libfive_interval` by value → out-pointer |
| `shim_tree_eval_d` | original takes and returns `libfive_vec3` by value |
| `shim_tree_get_const` | `bool*` out-parameter becomes a 32-bit out-parameter |
| `shim_tree_render_mesh_st` | original takes `libfive_region3` by value; only the `_st` variant is exposed (AD-014) |
| `shim_mesh_verts`, `shim_mesh_tris`, `shim_mesh_vert_count`, `shim_mesh_tri_count` | keep struct layout out of hand-written JS offsets |
| `shim_tree_evaluator`, `shim_evaluator_update_vars` | original takes `libfive_vars` by value |

`wasm/exports.txt` lists the core exports, the shim exports and `_malloc`/`_free`
(comments allowed). The build appends every `LIBFIVE_STDLIB` symbol parsed from
the vendored header, so pin bumps bring new stdlib functions automatically
without touching the manifest. Stdlib functions whose parameters are `tvec2`/
`tvec3` are exported but not JS-callable; pointer-flattened variants are
`stdlib-bindings`' job (item 5), and the README records that explicitly.
`wasm/README.md` documents pointer width, out-pointer conventions, the mesh
accessor contract, and which entry points are deliberately absent
(`libfive_tree_render_mesh`, `render_mesh_coords`, slices/pixels, save/load,
`libfive_git_*`) so the JS layer cannot accidentally depend on them.

This manifest is the "surface freeze" the roadmap assumes: changes to it are
review events, and `js-package-core` types against it.

### D7. Tests run against the built artifact in Node, not a second wasm binary

Both harnesses are dependency-free ESM scripts (`node:assert`, `node:fs`) that
import `dist/libfive.js`, pass `wasmBinary` read from disk (proving the loader
escape hatch and avoiding glue-path assumptions), and call raw exports through
the shim.

- `scripts/test-smoke.mjs`: verify every manifest symbol is callable, call the
  flat stdlib function `emptiness` (proves stdlib linkage), build
  `sqrt(x²+y²+z²) − r` with opcodes, evaluate at the center/outside, mesh via
  `shim_tree_render_mesh_st`, assert non-zero counts, indices in range, and
  vertex positions near radius `r`; also round-trip a printed tree and free
  everything. Non-zero exit on any failure.
- `scripts/test-interval.mjs`: cases from the `interval-rounding` spec —
  `exp` over `[0,1]`, `sin` over `[0,π]`, `1/x` over `[1,2]`, `1/x` across
  zero, `sqrt`/`log` over a region crossing their domain edge, and a mixed
  `exp(sin(x)) + 1/(y+2)` tree over a wide region. Containment is checked
  against dense sampling of the true function inside the region; tightness is
  checked with per-case caps (e.g. `exp` width < 1.75, `sin` width < 1.01,
  reciprocal width < 0.51). Undersized bounds fail containment, which is exactly
  the fault AD-015 warns about.

Testing the artifact rather than a second C test binary keeps one compile and
one wasm module; the artifact's exports are the contract callers use.

### D8. CI invokes the real build and caches pinned inputs (AD-020)

`build-wasm.yml` replaces the scaffold guard with an unconditional
`bash scripts/build-wasm.sh`, caches `build/cache`, `build/deps` and
`vendor/libfive` keyed on `vendor/libfive.lock` + `scripts/deps.lock` +
`vendor/patches/*`, appends the printed digest and artifact size to
`$GITHUB_STEP_SUMMARY`, and keeps uploading `dist/`. `publish-npm.yml` is left
as-is: its existing call to the same script is now real. The workflow remains
triggered on push/PR/dispatch, so the build is continuously exercised but
publishing still waits for `package.json`.

### D9. Patch and pin bookkeeping (AD-016, AD-021)

The three new patches are added to `vendor/patches/`, listed in
`patches=` in `vendor/libfive.lock`, and the combined `patch_digest` is
recomputed. `scripts/vendor-libfive.sh --force` then prints the new tree digest,
which is recorded in `vendor/VENDOR.md`; `--check` must pass afterwards. No
vendored file is hand-edited.

### D10. Decisions recorded as AD-022 and AD-023; baseline docs updated

`docs/decisions.md` gains:

- **AD-022 — Wasm artifact and export-surface mechanics**: static archives +
  single `emcc` link, explicit export manifest with per-symbol link roots,
  inline single-worker meshing under Emscripten, `_st`-only meshing, frozen
  core ABI; implements AD-004/AD-008/AD-014/AD-019, supersedes nothing.
- **AD-023 — Software interval rounding implementation**: why stock Boost
  policies fail, the double-evaluate + outward-`nextafter` policy, the
  acceptance suite, and the documented fallback; implements AD-015, supersedes
  nothing.

`docs/build-system.md` is updated to the concrete pipeline (script stages,
library type, link roots, test harnesses, LTO/closure outcome, flavor outputs),
`docs/architecture.md` gains the `wasm/` file map (shim, export manifest, interval
header) and the surface-freeze note, `docs/roadmap.md` item 2 status is updated
after acceptance, and the README development table gains the build/test entry
points.

Assumption (recorded rather than asked): roadmap item 5 owns stdlib pointer
shims and the generated TS wrappers; this change deliberately stops at exported
C stdlib symbols plus a documented caveat, keeping the change's test surface
small and the roadmap boundary intact.

## Risks / Trade-offs

- **First compilation may surface new porting failures.** → Each known hazard
  has a patch and a test; failures are fixed by editing the carried patches
  (never the tree), re-vendoring, and repeating on the verification server.
- **Incomplete `std::async` coverage.** → The four reachable sites were
  enumerated from the v1 path; acceptance includes a successful mesh in Node and
  a scan showing no pthread imports, so a missed site fails loudly.
- **Interval widening could be too wide and slow meshing.** → Tightness caps per
  case; if violated, reduce to one-ulp widening (already the choice) or refine
  specific functions; the fallback is the documented vendored-header route, not
  fenv.
- **Custom Boost policy interface drift.** → The header is compiled by the same
  Emscripten build as the kernel and exercised by every interval test; a
  compile-time failure is immediate, and the policy is deliberately small.
- **Export-list drift when the pin bumps.** → Stdlib symbols are derived from
  the header at build time; the core manifest is reviewed, and the smoke test
  asserts every manifested symbol exists.
- **Artifact size.** → Measure size and digest on every build; LTO adopted if
  tests stay green; no closure compiler in v1.
- **CI cost (Eigen/Boost and Emscripten setup).** → Cache archives and trees
  keyed on the lock files; the build script is idempotent.
- **`-sFILESYSTEM=0` with compiled-but-unreachable file code.** → Only the v1
  surface is linked as a root; the link step proves no missing syscalls, and the
  smoke test exercises the reachable paths.

## Migration Plan

Purely additive for a scaffold: add scripts/shim/spec/ADR/docs and replace the
build workflow's no-op guard. Rollback is deleting the new files, reverting the
patches/lock/VENDOR edits and the workflow, and restoring the guard; `dist/`
and `build/` are gitignored, so no consumer state exists. The artifact is not
published until roadmap item 8.
