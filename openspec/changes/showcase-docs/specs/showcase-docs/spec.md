# Spec Delta

## Purpose

Provide user documentation for `libfive-wasm` on the GitHub Pages site: an
overview, getting-started and concept tutorials, a three.js/3D-library
integration article, and a TypeDoc-generated API reference — all rendered by
the showcase application in its own design system and deployed with the
existing Pages workflow (AD-029).

## ADDED Requirements

### Requirement: Docs section uses the showcase design system

The site SHALL render the user documentation as an integrated section of the
showcase application at `#/docs/…` hash routes, using the same header, footer,
typography and color tokens as the gallery and demo pages, without loading a
separate documentation site, iframe or third-party theme.

#### Scenario: Docs landing renders in the site chrome

- **WHEN** a visitor opens `#/docs/`
- **THEN** the docs landing page renders between the same site header and
  footer as the gallery, in the site's visual style

#### Scenario: Moving between demos and docs

- **WHEN** a visitor navigates between a demo page and a docs page
- **THEN** the header, footer and overall visual design stay consistent and no
  separate application loads

### Requirement: Overview and getting-started guides exist

The docs SHALL include a library overview page and a getting-started tutorial
that covers installation, `init()`, building a first shape, meshing it, and
exporting STL, using only the package's public API.

#### Scenario: Overview page

- **WHEN** a visitor opens the overview page
- **THEN** it describes what the library is and its scope, and links to the
  getting-started tutorial and the API reference

#### Scenario: Getting-started tutorial

- **WHEN** a visitor follows the getting-started tutorial
- **THEN** its examples use only public exports and walk through install,
  `init()`, shape construction, meshing and STL export in order

### Requirement: Concept tutorials cover the core ideas

The docs SHALL include tutorials for the library's most important concepts,
at minimum: mesh resolution (`res` as the inverse of the minimum feature
size), the Shape API with CSG chaining and number coercion, the memory and
object lifecycle rules (explicit `free()`, use-after-free errors, zero-copy
views), evaluation, Web Worker usage, and bundler integration.

#### Scenario: Concepts section

- **WHEN** a visitor opens the concepts part of the docs navigation
- **THEN** every concept listed above has a page or clearly addressed section

#### Scenario: Concept pages match documented semantics

- **WHEN** a concept page explains behavior the README also documents
- **THEN** both describe the same semantics (for example, larger `res` means
  finer detail and slower meshing)

### Requirement: Three.js integration article exists

The docs SHALL include an article on integrating the package with JavaScript
3D libraries, containing a worked three.js example that renders a meshed shape
and covers buffer transfer to geometry attributes, the vertex/index layout,
shading-normal handling, and disposing copied buffers.

#### Scenario: Article shows a complete example

- **WHEN** a visitor opens the integration article
- **THEN** it contains a complete three.js example that meshes a shape, feeds
  copied vertex/index buffers into a geometry, renders it, and disposes the
  copies

#### Scenario: Article respects the memory rules

- **WHEN** the article transfers mesh data to a 3D library
- **THEN** it copies buffers (or documents view lifetime) consistently with
  the package's documented zero-copy and `free()` rules

### Requirement: Generated API reference

The docs SHALL include an API reference generated by TypeDoc from the
package's TypeScript entry point, converted to markdown and rendered through
the same docs pipeline as the guides, covering the package's documented public
exports.

#### Scenario: Reference is generated from source

- **WHEN** the docs build runs
- **THEN** TypeDoc generation succeeds against the current package source and
  emits reference pages for the package's public exports

#### Scenario: Reference is readable in the docs section

- **WHEN** a visitor opens an API reference entry
- **THEN** the entry renders in the docs design with a link back into the docs
  navigation

#### Scenario: Generation failure fails the build

- **WHEN** TypeDoc generation fails or produces no reference pages
- **THEN** the site build fails and nothing is deployed

### Requirement: Docs navigation and deep links

The docs SHALL provide a navigation listing all guide pages and API reference
sections, and every docs page SHALL be reachable at a stable, deep-linkable
hash route.

#### Scenario: Deep link opens a docs page

- **WHEN** a visitor opens a docs deep link directly
- **THEN** that page renders with the correct content selected in the
  navigation

#### Scenario: Unknown docs path

- **WHEN** a visitor opens an unknown `#/docs/…` path
- **THEN** the site shows its not-found page

### Requirement: Header Docs link targets the docs section

The site header's "Docs" link SHALL open the docs landing route instead of the
repository README.

#### Scenario: Clicking Docs in the header

- **WHEN** a visitor activates the "Docs" header link
- **THEN** the docs landing page opens

### Requirement: Docs deploy with the showcase

The docs SHALL be built as part of the site build — including the generated
API reference step — and deployed by the existing Pages workflow from the
tested artifact, with no second deployment path and no registry fetch of
`libfive-wasm`.

#### Scenario: Pages build includes docs

- **WHEN** the Pages workflow builds the site
- **THEN** the docs build step runs before the site bundle step and its output
  is included in the deployment

#### Scenario: Docs work on the deployed site

- **WHEN** a visitor opens a docs route on the deployed site
- **THEN** guide and API reference content renders without errors

### Requirement: Docs content is validated

The test suite SHALL validate the docs section: every page listed in the docs
navigation exists, links between docs pages resolve, and hand-written
TypeScript examples typecheck against the package's public types.

#### Scenario: Navigation matches content

- **WHEN** the docs validation suite runs
- **THEN** every navigation entry resolves to an existing page and every
  intra-docs link resolves

#### Scenario: Broken example fails CI

- **WHEN** a docs example references an export or signature that does not
  exist
- **THEN** the validation suite fails
