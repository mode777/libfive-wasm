# Design

## Context

See `proposal.md` for motivation and the three spec deltas for contracts. The
current state that shapes the approach:

- The package suite (`vitest`) already loads the real `dist/libfive.wasm` and
  exercises the public `Shape`/stdlib API (`tests/support/artifact.ts`,
  `tests/kernel.test.ts`, `tests/meshing.test.ts`), so the golden harness can
  reuse that path instead of inventing a second artifact loader.
- `scripts/build-wasm.sh` currently runs two standalone Node suites
  (`test-smoke.mjs`, `test-interval.mjs`) immediately after linking, while
  `build-wasm.yml` installs dev dependencies only *after* the build and then
  runs `npm test`. The golden suite needs the public TS API, so it belongs to
  the vitest suite.
- Goldens depend on the vendor pin (AD-016), the software interval policy
  (AD-015/AD-023), Boost/Eigen pins (AD-021) and the Emscripten version
  (AD-013). They must be regenerated deliberately when any of those change.

## Goals / Non-Goals

**Goals:**

- A small, reviewable golden corpus that catches sub-ulp mesh drift.
- Exact, deterministic comparison with no tolerance knobs that could be
  loosened accidentally.
- Goldens that are generated by a single documented command and read-only in
  every other run.
- Fault injection that proves the harness detects one-float32-ulp changes.

**Non-Goals:**

- Pixel/screenshot rendering, image comparison, or browser golden captures.
- Native cross-check builds (`--host=native` stays a later convenience).
- Replacing the interval bounds suite; the two gates complement each other.
- Any change to the meshing algorithm, API or ABI.

## Decisions

### D1 — One JSON golden per scene, counts plus a float32-prefix hash (AD-025)

Each scene gets `tests/goldens/<scene>.json`:

```json
{
  "schemaVersion": 1,
  "scene": "sphere",
  "region": { "min": [-1.5, -1.5, -1.5], "max": [1.5, 1.5, 1.5] },
  "res": 12,
  "vertCount": 1234,
  "triCount": 2345,
  "hashedComponents": 6144,
  "vertexHash": "…64 hex chars…",
  "vendorCommit": "918387a9220dbac2f7ab32fb35e274c6794439cf"
}
```

The hash is SHA-256 over the first `min(vertCount * 3, 6144)` float32
components of the mesh's vertex view, serialized in the platform's little-endian
byte order (wasm is little-endian; Node runs on x86/ARM little-endian in CI).
The prefix is large enough to cover the BRep marker plus the first ~2000
vertices of each scene and small enough to keep files and hashing trivial.
Counts catch topology changes even when the hashed prefix happens to match.
No tolerance is applied: `Float32Array` values are compared through their bits.

Alternatives considered: full vertex hash (larger scenes make capture output
noisier but detection is equivalent; a prefix keeps the goldens small and
diff-friendly), a perceptual/quantized hash (rejected — hides the drift the
suite exists to catch), and per-scene PNGs (rejected — no browser dependency in
the build gate, and images are harder to review).

### D2 — Scenes are built through the public API, with fixed inputs

`tests/support/golden.ts` exports the scene list and one builder per scene,
using only `init()`, stdlib functions and `Shape` methods (`sphere`, `gyroid`,
blend methods, `text`) plus `shape.mesh({ region, res })`. The four scenes are:

| Scene | Construction | Region | res |
|---|---|---|---|
| `sphere` | `sphere(1)` | `[-1.5, 1.5]³` | 12 |
| `gyroid` | `gyroid(2 * Math.PI, 0.4)` | `[-2, 2]³` | 8 |
| `blended-union` | two spheres blended with `blend` | `[-2.5, 2.5]³` | 10 |
| `text` | `text('lf', [-0.8, -0.5, 0])` | `[-1.5, 1.5]³` | 10 |

The helper frees every `Shape` and `Mesh` in `finally` so capture runs do not
leave wasm memory pinned, and loads the artifact from `dist/` exactly like the
existing package tests. Scene definitions live in one file; changing a region,
resolution or expression requires a capture.

Alternatives considered: raw C calls (rejected — the roadmap asks for the
public API, and public-API scenes also cover coercion/marshalling), and reading
scene definitions from JSON (rejected — builders are typechecked and reviewers
see the exact geometry).

### D3 — Capture is explicit, atomic and read-only by default

`compareGolden(actual, golden)` is a pure function; the test calls it and only
writes when `GOLDEN_CAPTURE=1` is set. In capture mode the helper serializes the
new golden, writes it through a temp file + rename, and the test still reports
the written scenes. Without the switch, a missing golden is a failure (never an
implicit capture). `scripts/capture-goldens.mjs` sets the switch and runs
`vitest run tests/golden.test.ts`; `npm run golden:capture` invokes it. The
script refuses to run when `dist/libfive.wasm` is absent and prints the vendor
pin and artifact digest so the capture is traceable.

Alternatives considered: a separate capture binary importing TS directly
(rejected — duplicates the test harness and drifts), and updating goldens from
the test when a mismatch is hit (rejected — silently blesses regressions).

### D4 — Fault injection perturbs one float32 ulp

`tests/golden.test.ts` includes a self-test that meshes the sphere scene, makes
a copy of its first vertex component, and increments/decrements the raw
float32 bits by one (`nextafter` semantics implemented with a `DataView`). It
then calls `compareGolden` with the original golden and asserts that it throws.
This is the smallest change the artifact can produce; anything an interval
policy change does to vertex placement is at least this large, so a passing
self-test demonstrates the comparator's sensitivity. The self-test is part of
`npm test` and therefore of CI.

Alternatives considered: building a second artifact with a deliberately broken
header (rejected — doubles build time and requires a test-only C variant in the
production tree); and perturbing a hash by hand (rejected — does not exercise
the comparator's mesh path).

### D5 — Build and CI run the golden suite against the current artifact

`build-wasm.sh` runs the golden suite after the smoke and interval suites when
`node_modules/.bin/vitest` exists (`--no-tests` skips it like the others). CI
installs dev dependencies *before* `build-wasm.sh` (they only depend on
`package-lock.json`), so the release build always runs the golden suite, then
the existing `npm test` repeats it as part of the full package suite.
Goldens are captured only from a release artifact; the debug flavor is not
compared (optimization differences are not part of the reviewed output).

Alternatives considered: running `npm ci` after the build and keeping goldens
only in `npm test` (rejected — a golden failure would then be attributed to the
package step, and the build itself would not gate on mesh output), and using a
separate workflow (rejected — it could run against a stale artifact).

### D6 — ADR and docs in the same change

`docs/decisions.md` gains **AD-025** (golden mesh verification protocol).
`docs/build-system.md` documents the golden pipeline, capture/recapture
procedure and fault injection; `README.md` gains the contributor verification
commands; `docs/roadmap.md` flips change 6 to Done when the gate passes.

## Risks / Trade-offs

- **Goldens are platform-sensitive** (compiler/toolchain/link layout) → they
  are captured from the pinned CI toolchain and only claimed for that
  toolchain; recapture is a reviewed event, and the interval/smoke suites stay
  platform-neutral complements.
- **One-ulp self-test may not exercise every scene** → it exercises the shared
  comparator, and every scene runs through the same comparison code; the
  sphere's mesh is representative.
- **Capture-mode accidents** → `GOLDEN_CAPTURE` is a separate npm script and
  the test prints a loud capture notice; normal runs never write.
- **Hash prefix misses a change after component 6144** → triangle counts plus
  the prefix catch the common drift, and scenes are sized so the prefix covers
  the vast majority of their vertices; full-mesh hashing remains a one-line
  change if needed later.
- **Debug/release divergence** → debug builds are explicitly out of the golden
  gate; the release artifact is the shipped one.
